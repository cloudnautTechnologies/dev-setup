# Design: Cloudnaut Dev Setup v0.1

## Overview

The product is a Node.js (>= 22) CLI with no dependencies plus a tree of packaged content. A developer checks out a release tag of this repository, then runs `preview`, `apply`, or `doctor` against a project directory. All three commands share one pipeline: load and verify the release manifest, resolve the profile and options into a desired state, read the project's current state, compute a plan by three-way comparison against the project's lock file, and then either print the plan (`preview`), execute it transactionally (`apply`), or check the result of a previous apply (`doctor`).

The stack is locked once this design is approved: Node.js >= 22 built-ins only (`node:fs`, `node:path`, `node:crypto`, `node:util` `parseArgs`, `node:child_process` for `doctor` tool checks, `node:test`/`node:assert` for tests); plain JavaScript as ES modules (`"type": "module"`); no TypeScript, no bundler, no lint dependency. Plain JS avoids a build step, which keeps a tagged checkout runnable as-is on all three operating systems.

Packaged content lives only under `profiles/` and `powers/`. The repository's own `.kiro/` holds only this spec. The packaged files mirror the target project layout so a file's target path is its path relative to the profile's `files/` directory.

## Recorded decisions

| ID | Decision | Reason |
| --- | --- | --- |
| D1 | ES modules, plain JS, `node --test`. | No build step, no dependencies. |
| D2 | Entry: `bin/dev-setup.js`, run as `node bin/dev-setup.js`. `package.json` also has a `bin` entry but the package is `private` and unpublished. | Release channel is Git tags only (A2). |
| D3 | Release manifest `release-manifest.json` is generated by `scripts/generate-manifest.js` from `profiles/*/profile.json` plus the files on disk, committed, and verified by `--check` in tests. The CLI verifies packaged file hashes against it at startup. | A stale or corrupt checkout fails loudly instead of installing wrong content. |
| D4 | Upgrade conflict handling writes an incoming copy under `.cloudnaut/incoming/` and leaves the local file untouched. Not a `.new` file beside the original. Entry copies use `.cloudnaut/incoming/<target>.<entry-name>.json`. | Side-by-side `.new` files in `.kiro/steering/` or `.kiro/skills/` risk being loaded by Kiro; `.cloudnaut/` is never read by Kiro. The copy is a normal Git-reviewable file. |
| D5 | Rollback strategy for an interrupted apply is roll-back, then redo, not roll-forward. | Simpler invariant: after recovery the project equals its pre-apply state, and a normal apply follows. |
| D6 | Options are sticky and recorded in the lock. | Upgrades need no flags, and the hook command is not lost. |

A committed copy plus a failing test keeps one edit point without runtime machinery. |
| D9 | MCP server key names: `aws-knowledge-mcp` (matches upstream's Kiro deeplink) and `codegraph`. | Documented in sources. |

| D11 | AWS/CDK and Connect steering use `inclusion: auto`. | Documented mode; "load when relevant." Whether Kiro matches reliably is a live-IDE check. |
| D12 | The hook is static: `enabled: true`, `timeout: 600`, `action.command` is the fixed string `node .cloudnaut/run-verify.cjs`. | D13 | `doctor` locates `codegraph` by scanning `PATH` (and `PATHEXT` on Windows) without executing it. The probe is the only third-party process the CLI starts, it is optional, and the CLI's own code opens no connections (R3.4, R8.6). Output format and offline behavior are unverified. |
| D14 | Shared files (`mcp.json`, `extensions.json`, `.gitignore`) are edited as text: only the inserted or replaced range changes. Detected EOL, BOM, and indentation are reused. New files use LF. | Minimal diffs in Git on Windows. |
| D15 | Missing owned file on apply means "restore". To take the new upstream version of a conflicting file, delete the local file and apply. | One simple, documented resolution gesture; no extra flags. |
| D16 | No `--force`/`--accept` flags in v0.1. | Collisions are resolved by editing the project, which is reviewable in Git. |
| D17 | Exit 0 for a successful apply even when review items remain. `doctor` surfaces them as INFO. | Conflicts are preserved and non-destructive; script-friendly detection comes from `--json` (`summary.reviewItems`). |
| D18 | The CLI reads only the target project, the checkout it runs from, and `PATH`. It never reads `os.homedir()` contents. It reads `os.homedir()` string only for the home-refusal check (R18.2). | R18. |
| D19 | CI matrix Node 22, 24, 26; actions pinned by major tag (`@v7`). | Maintainer may pin by SHA (flagged in the final report). |
| D21 | `mcp.json` uses text-level insertion with the same scanner as `extensions.json` (`jsontext.js`), not parse and `JSON.stringify`. | Preserves compact arrays, inline objects, and blank lines in unrelated entries so the Git diff is only our entry (finding 6, option a). |
| D22 | Journal id is 8 lowercase hex characters (`crypto.randomBytes(4)`). The journal is write-ahead with an explicit `state`, and carries an owner record. | Findings 1 to 3. |
| D23 | `doctor --no-exec` exists. | Lets users and CI run `doctor` with no third-party process. |
| D24 | Vendored Ponytail files are exempt from the content lint, guarded by a hash check instead. Upstream hosts are also allowlisted for `SOURCE.md` and docs. | The vendored bytes cannot be edited (finding 11). |
| D25 | Declined recommendations are honored for owned items: `DECLINED` is a collision only for items with no lock entry. Opt-outs are `unwantedRecommendations` for the extension and `"disabled": true` for an MCP entry, documented in `docs/releasing.md`. | Upgrades must not block on a developer's deliberate opt-out; no `--force` is needed (D16). |
| D20 | `.gitattributes`: `* text=auto eol=lf`. | Stable hashes and clean diffs on Windows. |


Each `profile.json` is the hand-written input: `{ "includes": [...], "mcpEntries": [{name, source}], "extensions": [...] }`. The generator walks `profiles/<name>/files/**`, maps each file to its target path, computes the normalized SHA-256, and writes the manifest. `generate-manifest.js --check` regenerates in memory and exits 1 on any difference. Profile inclusion is resolved by depth-first expansion in `manifest.js` (`connect` => `core`, `aws`, `connect`, deduplicated, ordered by inclusion). The generator rejects cycles, unknown includes, duplicate target paths, targets outside the allowlist (R13.9), and MCP entry names outside `[A-Za-z0-9._-]` (they become incoming-copy file names).

At startup, `manifest.js` verifies every packaged file that the run will use against the manifest hash; any mismatch is a fatal `INTEGRITY` error (exit 6) with "checkout is modified or corrupt; re-checkout the release tag".

## Desired state, current state, and the plan

### Items

Every managed thing is an item with a stable `id`:

| Kind | Id format | Hash input |
| --- | --- | --- |
| `file` | `file:<target>` | normalized text (CRLF to LF) |
| `json-entry` | `json:<file>#/mcpServers/<name>` | canonical JSON of the entry value |
| `jsonc-item` | `jsonc:<file>#/recommendations/<value>` | the string value |
| `line` | `line:<file>#<line>` | the line text |
| rendered file (`verify-command.json`) | `file:<target>` | normalized rendered text |

### Plan data model (shared by preview and apply)

`buildPlan(input)` is pure with respect to the project: it reads files but writes nothing. It returns:

```js
Plan = {
  schemaVersion: 1,
  tool: { name, version },
  project: "<real project path>",          // appears in --json output; never written to the lock
  profile: "aws",
  resolvedProfiles: ["core", "aws"],
  options: { withCodegraph: false, withPonytail: false, verifyCommand: null },
  fromLock: null | { version, profile, options },
  actions: [ Action ],
  writes: [ Write ],                        // file-level, derived from actions
  collisions: [ Collision ],
  reviewItems: [ ReviewItem ],
  recovery: null | { journalId, state },    // pending journal found
  summary: { create, update, adopt, unchanged, keepLocal, restore, remove, collisions, reviewItems }
}
Action = {
  id, kind, target, pointer?, owner,        // owner: "core" | "aws" | "connect" | "codegraph" | "ponytail" | "verifyHook"
  op: "create"|"update"|"adopt"|"unchanged"|"keep-local"|"restore"|"remove"|"skip-preexisting",
  baseHash, localHash, incomingHash, resultHash,   // null where not applicable
  incomingCopy?: ".cloudnaut/incoming/…",       // files: <target>; JSON entries: <target>.<entry-name>.json
  reason: "…"
}
Write = {
  path,                                      // project-relative, posix
  realPath,                                  // resolved absolute path to write (symlink-resolved, inside root)
  mode: "create"|"replace"|"delete",
  content,                                   // string, never serialized to --json
  expectBeforeHash,                          // hash of file bytes (raw) at planning time, null if absent
  resultHash                                 // normalized hash of content
}
```

`--json` output serializes everything except `content`. `apply` calls `buildPlan` once, prints/serializes it, then passes the same object to `executePlan(plan)`. Preview and apply differ only in the last step, which satisfies R13.5.

Planning steps:

1. `paths.resolveProject(arg)`: realpath, directory check, home refusal.
2. `lock.read(project)`: absent, or validated lock. Unknown `schemaVersion` is fatal (exit 6). Lock version greater than tool version is exit 2 (downgrade). Locked profile not contained in the requested profile's resolved set is exit 2 (narrowing).
3. `recover.detect(project)`: if `journal.json` or `journal.recovering.json` exists, `plan.recovery` is set to `{ journalId, state, owner, ownerStatus }`, where `ownerStatus` is `alive`, `dead`, `foreign-host`, `unreadable-old`, or `unreadable-new` (journal owner check). `preview` prints the notice and exits 5. `apply` follows the journal owner check: it exits 5 for `alive`, `foreign-host`, and `unreadable-new`, and runs recovery then re-reads state for `dead` and `unreadable-old`.
4. Merge options: flags override lock options, lock fills omissions (D6). Validate `--verify-command`.
5. Build the desired item list from the manifest (profile files, MCP entries, extension IDs, features; with `--verify-command`: the hook, the runner, and the rendered `verify-command.json`).
6. For each desired item, read the current state (`state.js`): file text or absence, JSON entry value or absence, JSONC array contents, line presence. All target paths pass `paths.guard()` first (symlink policy). A guard failure is a fatal exit 3 before anything else is evaluated.
7. Classify each item (below).
8. Add `remove` or `keep-local` actions for items in the lock that are no longer desired.
9. Derive `writes[]`: file items map one to one. Shared files (`mcp.json`, `extensions.json`, `.gitignore`) collect all their item actions into one ordered splice list and are written once.
10. Lock write: the new lock content is computed, and if it equals the existing lock bytes, no lock write is planned (idempotency). Commit state is never inferred from the lock (journal `state` is the only signal), so an unchanged lock is safe.

### Classification

Without a lock entry for the item (initial install, or newly added by an upgrade):

| Current state | Result |
| --- | --- |
| absent | `create` |
| present and hash equals incoming | `adopt` (recorded `adopted: true`, no write) |
| present and differs | collision `EXISTS_DIFFERENT` |
| (extension ID / ignore line) present | `skip-preexisting` (recorded `preexisting: true`, not owned) |

With a lock entry, apply the table in R16.1 using `base` = lock hash, `local` = current hash, `incoming` = manifest hash. `unchanged` and `keep-local` produce no write. `update` and `restore` produce a write. A conflict yields `keep-local`, a `Write` of the incoming copy, and a `ReviewItem`. The incoming copy path is `.cloudnaut/incoming/<target>` for files and `.cloudnaut/incoming/<target>.<entry-name>.json` for JSON entries (for example `.cloudnaut/incoming/.kiro/settings/mcp.json.aws-knowledge-mcp.json`; the entry name is restricted to `[A-Za-z0-9._-]` by the generator, so no `#` or `/` appears in a file name). Extension IDs and `.gitignore` lines never conflict (they are only inserted) and have no incoming copies. Resolution paths: `adopt` (local now equals incoming), `restore` (the developer deleted the local file or entry), and `update` (a later release equals the base again and local equals base) each add a `delete` write for the incoming copy (when it exists) and drop the item's `unresolved` lock entry in the same transaction. If the incoming copy was deleted by hand while the conflict persists, the next apply rewrites it.

For shared-file items (JSON entry, JSONC item, line), "local" is the value of just that item, so edits elsewhere in the file are never conflicts (R16.7). An absent owned JSON entry is `restore`.

### Merge strategies per file kind

- **Whole file** (steering, skills, docs, Ponytail, hook, runner, `verify-command.json`): text replaced by the incoming text via temp file and rename. No partial merging; local edits are preserved by `keep-local` and incoming copies, never by line merging.
- **Shared scanner (`jsontext.js`)**: a small tolerant scanner (strings with escapes, `//` and `/* */` comments, punctuation, literals, numbers) that returns token ranges, plus a structural walk that locates the root object, a named property, and its value range. It never re-serializes a document; every edit is a splice `(start, end, replacement)` over the original text, and all splices for one file are applied from the end to the start so offsets stay valid. Detected per file: BOM, EOL (first line break; default LF), and indent unit (first indented line's leading whitespace; default two spaces).
- **Common insertion rules** for appending an element to an array or a property to an object (used by both files below):
  1. Insert `,` immediately after the last existing element token, unless a comma already follows it.
  2. Multi-line container: the new element goes on a new line inserted after the end of the physical line that holds the last element (including any trailing `//` or `/* */` comment on that line, so the comment stays attached to its element), using the last element's indentation. Standalone comments between the last element and the closing bracket stay after the new element.
  3. Single-line non-empty container (`["a", "b"]`, `{ "a": 1 }`): insert `, <element>` immediately after the last element token, before the closing bracket, keeping the line style.
  4. Empty container (`[]`, `{}`): if the closing bracket is on the same line, replace with a multi-line container in the file's indentation; if the container holds only comments, insert the new line before the closing bracket.
  5. A trailing comma after the last element is kept as a style: the new element also gets a trailing comma.
- **`mcp.json` (text-level property edit, D21)**: the file must be strict JSON: `JSON.parse` after stripping the BOM, root an object, `mcpServers` absent or an object; any comment, parse error, or wrong shape is collision `UNPARSEABLE`. The scanner finds `mcpServers` and its properties. For a new entry, append `"<name>": <value>` using the common insertion rules; the value text is `JSON.stringify(value, null, <indent unit>)` re-indented to the container's depth and EOL. If `mcpServers` is missing, a `"mcpServers": { … }` property is appended to the root object by the same rules; if the file is absent, it is created as `{\n  "mcpServers": {\n    "<name>": …\n  }\n}\n`. For an owned entry that must change (`update` or `restore` of a changed value), only that property's value range is replaced. Nothing else is touched, so unrelated entries keep compact arrays, inline objects, blank lines, and exact spacing. The tests assert byte equality of everything outside the edited range against a fixture with deliberately compact and irregular formatting.
- **`extensions.json` (JSONC text edit)**: uses the scanner and the common insertion rules on the `recommendations` array. Cases:
  1. ID already present (string compare, case-insensitive): no edit, `skip-preexisting`.
  2. Non-empty array: common rules 1, 2, 3, and 5.
  3. Empty array: common rule 4.
  4. `recommendations` missing: append `"recommendations": [ "<id>" ]` to the root object by the common rules for objects.
  5. Root not an object, `recommendations` not an array of strings, or any scanner error: collision `UNPARSEABLE`. ID in `unwantedRecommendations`: collision `DECLINED` when the lock does not own the item; when it does, the item is `keep-local` with INFO `DECLINED_LOCALLY` and the missing-item `restore` rule (D15) does not apply to it.
  New file content: `{\n  "recommendations": [\n    "amazonwebservices.aws-toolkit-vscode"\n  ]\n}\n`. Ownership of the inserted ID is recorded; the lock hash is the SHA-256 of the ID string. The item is only inserted, never rewritten: upgrade is `unchanged` while the ID is present, and `restore` if the developer removed it. Byte-exact tests: trailing line comment on the last element; block comment between the last element and `]`; single-line array; empty `[]`; array containing only comments; trailing comma; missing key; CRLF; BOM; ID present; ID declined; malformed.
- **`.gitignore` (line append)**: file split into lines on `\n` or `\r\n`. A line equal to the desired line after trimming trailing whitespace (also `.codegraph` and `/.codegraph/` count as equivalent) means `skip-preexisting`. Otherwise append the line, preceded by a line break if the file does not end with one, using the file's EOL. Creating the file when absent. Only active with `--with-codegraph`.
- **Hook, runner, and command file**: the hook file and `run-verify.cjs` are static packaged files (whole-file semantics). `verify-command.json` is rendered by `hook.js` as `JSON.stringify({ "command": <validated command> }, null, 2) + "\n"`. Because the user's text is only ever encoded by the JSON encoder, never substituted into other text, quotes, backslashes, `%`, `$`, and Unicode are safe (R7.5), and the hook JSON contains no user input. Changing `--verify-command` later is an `update` if `verify-command.json` is unmodified, a conflict if the developer edited it. `hook.js` also computes the secret-pattern warning (R7.4).

### Conflict taxonomy

Collisions (preflight, exit 2, no writes):

| Code | Meaning | Resolution message |
| --- | --- | --- |
| `EXISTS_DIFFERENT` | A non-owned file exists at a target with different content | Move or merge it, or rename it, then re-run |
| `MCP_ENTRY_DIFFERENT` | `mcpServers.<name>` exists with a different value, not owned | Rename the existing entry, or make it equal, then re-run |
| `UNPARSEABLE` | `mcp.json` or `extensions.json` cannot be parsed or has the wrong shape | Fix syntax; for `mcp.json` it must be strict JSON |
| `DECLINED` | Extension listed in `unwantedRecommendations` and not owned in the lock (first install or newly added item only) | Remove it from that list if you want the recommendation |
| `TYPE_MISMATCH` | Directory where a file is needed, or the reverse | Rename the path |
| `CHANGED_DURING_APPLY` | A target changed between planning and writing | Re-run |

Fatal refusals (not collisions):

| Code | Exit | Meaning |
| --- | --- | --- |
| `USAGE` | 1 | Bad arguments |
| `ESCAPE` | 3 | A target resolves outside the real project root through a symlink, or the project is the home directory or inside `~/.kiro` |
| `DOWNGRADE`, `NARROWING` | 2 | Older release or smaller profile than the lock |
| `RECOVERY_PENDING` | 5 | Pending journal (preview, doctor), or concurrent apply |
| `INTEGRITY`, `LOCK_INVALID`, `INTERNAL` | 6 | Corrupt checkout or lock, or unexpected error |

Owned items that the developer declined are not collisions: an owned extension ID in `unwantedRecommendations` is `keep-local` with INFO `DECLINED_LOCALLY` (no write, no restore), and a local `"disabled": true` on an owned MCP entry is an ordinary local edit (`keep-local`, or a conflict only if the incoming value also changed). These are the two supported opt-outs (D25).
Review items (not errors, exit 0): `CONFLICT` (three-way conflict, incoming copy written), `LOCALLY_MODIFIED` (local differs, incoming unchanged), `REMOVED_UPSTREAM_KEPT` (file dropped upstream but locally modified).

### Exit codes

| Code | Name | Used by |
| --- | --- | --- |
| 0 | OK | success (with or without review items); `doctor` with no BROKEN findings |
| 1 | USAGE | bad arguments or flags |
| 2 | COLLISION | preflight collisions, downgrade, narrowing, changed during apply. No writes |
| 3 | UNSAFE_PATH | symlink escape, home directory, `~/.kiro` |
| 4 | DOCTOR_BROKEN | `doctor` found broken config |
| 5 | RECOVERY | pending journal (preview), concurrent apply, or recovery could not finish |
| 6 | INTERNAL | integrity failure, invalid lock, unexpected exception |

## Lock file schema

Path `.cloudnaut/dev-setup.lock.json`. Committed to Git. Keys are sorted at write time; arrays are sorted by `id`; 2-space indent; LF; trailing newline.

```json
{
  "schemaVersion": 1,
  "tool": "cloudnaut-dev-setup",
  "version": "0.1.0",
  "profile": "aws",
  "options": { "withCodegraph": false, "withPonytail": false, "verifyCommand": null },
  "items": [
    { "id": "file:.kiro/steering/cloudnaut-core.md", "kind": "file", "target": ".kiro/steering/cloudnaut-core.md", "owner": "core", "sha256": "…", "adopted": false },
    { "id": "json:.kiro/settings/mcp.json#/mcpServers/aws-knowledge-mcp", "kind": "json-entry", "target": ".kiro/settings/mcp.json", "pointer": "/mcpServers/aws-knowledge-mcp", "owner": "aws", "sha256": "…", "adopted": false },
    { "id": "jsonc:.vscode/extensions.json#/recommendations/amazonwebservices.aws-toolkit-vscode", "kind": "jsonc-item", "target": ".vscode/extensions.json", "value": "amazonwebservices.aws-toolkit-vscode", "owner": "aws", "sha256": "…", "preexisting": true }
  ],
  "unresolved": [
    { "id": "file:.kiro/steering/cloudnaut-core.md", "incoming": ".cloudnaut/incoming/.kiro/steering/cloudnaut-core.md", "incomingSha256": "…", "sinceVersion": "0.2.0" },
    { "id": "json:.kiro/settings/mcp.json#/mcpServers/aws-knowledge-mcp", "incoming": ".cloudnaut/incoming/.kiro/settings/mcp.json.aws-knowledge-mcp.json", "incomingSha256": "…", "sinceVersion": "0.2.0" }
  ]
}
```

Rules: `items[].sha256` is the base hash used for the next three-way compare. For an unresolved conflict the item's `sha256` stays the old base (R16.3). `preexisting: true` items are listed for traceability but are not owned: they are never updated, restored, or removed. The lock holds no timestamps, absolute paths, or user names. The lock itself is never part of `items`. Validation (`lock.js`): `schemaVersion === 1`; `tool` matches; `version` is semver; `profile` is a known name; every item has a string `id`, `kind` in the enum, `target` that is a safe relative path (no `..`, no absolute, no backslash, inside the allowlist), and a 64-hex `sha256`; ids are unique. For `unresolved[]`, `incoming` is never trusted: `lock.js` re-derives the expected path from the item id with the same function that creates incoming paths, requires it to equal the stored value and to start with `.cloudnaut/incoming/`, and runs `paths.guard` on it before any delete is planned. A mismatch is `LOCK_INVALID` (exit 6).

## Transactional apply and recovery

### Files under `.cloudnaut/`

- `dev-setup.lock.json` (committed)
- `incoming/…` (committed for review, removed when resolved)
- `third-party/ponytail/…` (committed, only with Ponytail)
- `run-verify.cjs`, `verify-command.json` (committed, only with `--verify-command`)
- Transient, never committed, absent after a finished apply: `journal.json`, `journal.recovering.json`, `backup/<id>/…`, and temp files beside targets named `<name>.cloudnaut-tmp-<id>`. `<id>` is always 8 lowercase hex characters (`crypto.randomBytes(4).toString("hex")`); the temp-file pattern is `^.+\.cloudnaut-tmp-[0-9a-f]{8}$`. Doctor reports any transient file as BROKEN `TEMP_LEFTOVER`.

Scan scope (used by recovery and doctor to find stray temp files): the directory of every manifest target of every profile and feature (not only the planned ones), plus `.cloudnaut/` and its `incoming/` and `third-party/` subdirectories, non-recursive per directory. Created parent directories that were recorded in the journal are removed by recovery when empty.

### Journal schema (`.cloudnaut/journal.json`, private to `apply.js` and `recover.js`)

```json
{
  "schemaVersion": 1,
  "id": "9f3a0c1e",
  "toolVersion": "0.1.0",
  "owner": { "pid": 4242, "hostname": "dev-laptop", "startedAt": "2026-01-01T00:00:00.000Z" },
  "state": "staging",
  "createdDirs": [ ".cloudnaut", ".cloudnaut/backup", ".cloudnaut/backup/9f3a0c1e" ],
  "ops": [ { "path": ".kiro/steering/cloudnaut-core.md", "realPath": "<abs>", "mode": "create", "tmp": "<abs>.cloudnaut-tmp-9f3a0c1e", "backup": null, "beforeHash": null, "afterHash": "<raw sha256>" } ]
}
```

`state` moves `staging` to `applying` to `committed` and never backwards. The journal holds absolute paths and a timestamp; it is transient and never committed (the lock rule of "no absolute paths or timestamps" applies only to the lock).

### Apply algorithm (write-ahead)

Helper `journalWrite(j)`: write `journal.json.tmp-<id>`, fsync, rename over `journal.json`. Every rewrite happens before the action it announces ("intent first").

1. `buildPlan`. If `plan.recovery` is set, run the journal-owner check (next section) and either exit 5 or run `recover()`, then rebuild the plan. If `collisions.length > 0`, print them and exit 2 (nothing written). If there are no `writes` and no lock change, print "already up to date" and exit 0.
2. **Preflight re-check**: for every write with `expectBeforeHash`, re-read the file and compare. A mismatch is `CHANGED_DURING_APPLY` (exit 2, nothing written).
3. **Create the journal exclusively**: `mkdir -p .cloudnaut` (the one directory created before a journal exists, so it is never removed by recovery; it is harmless and holds the lock anyway), then `fs.openSync('.cloudnaut/journal.json', 'wx')` and write the initial body (`state: "staging"`, owner, empty arrays) in one `writeSync`, fsync. `EEXIST` here means another process won the race: exit 5. (If a journal existed at plan time, step 1 already decided.)
4. **Stage** (state `staging`). For each write sorted by path:
   a. For each missing parent directory, outermost first: append to `createdDirs`, `journalWrite`, then `mkdir`.
   b. Append the op (with its `tmp` and, for `replace`/`delete`, `backup` paths) to `ops`, `journalWrite`, then create the backup (copy to `.cloudnaut/backup/<id>/<path>`, creating backup directories after recording them) and the temp file (`writeFileSync` with `flag: 'wx'`, fsync, copy the existing file's mode for replacements).
   c. Checkpoint `during-stage:<i>` after each write.
5. **Switch to `applying`**: `journalWrite` with `state: "applying"`. Checkpoint `after-stage`.
6. **Commit**: iterate ops in order, with the lock op last (a lock op exists only when the new lock bytes differ from the current ones, and when it exists it is staged and renamed last; an unchanged lock is never rewritten, which keeps repeat apply idempotent). For `create`/`replace`: `fs.renameSync(tmp, realPath)`; on Windows `EPERM`/`EBUSY`/`EACCES` retry up to 5 times with 50 ms sleeps, then fail. For `delete`: `fs.unlinkSync(realPath)`. Checkpoint `after-rename:<i>`. The journal is not rewritten between renames (recovery decides per op by hash).
7. **Mark committed**: `journalWrite` with `state: "committed"`. This is the only commit signal. Checkpoints: `before-lock`, `after-lock`, `after-committed`.
8. **Finish**: delete leftover temp files (none expected), `backup/<id>/`, empty directories that `incoming/` or an emptied owned skill folder left behind, then `journal.json`. Checkpoint `before-journal-delete`. Print the summary.

### Failure handling during apply

Any exception after step 3 triggers `rollback(journal)` (the same function recovery uses) in a `catch` path and exits with the original error's code (usually 6; collisions detected late are exit 2). If rollback fails, the journal remains, the CLI exits 5 and prints "run apply again to recover; no data is lost: backups are in `.cloudnaut/backup/<id>/`". An exception in step 8 (after `committed`) does not roll back; the next run performs clean-up only.

### Journal owner check (concurrency versus crash)

When `plan.recovery` is set, `apply` decides in this order:

1. Journal parses and `owner.hostname === os.hostname()` and `process.kill(owner.pid, 0)` does not throw `ESRCH` (the process is alive; `EPERM` also counts as alive): exit 5, "another apply is running (pid N)". Nothing is touched. Pid reuse can make a dead owner look alive; the message then says how to remove `.cloudnaut/journal.json` by hand after checking.
2. Journal parses and the owner is on this host and dead: recover.
3. Journal parses and `owner.hostname` differs (shared or synced folder): exit 5 with manual instructions. No automatic recovery.
4. Journal does not parse (empty because of a crash between `open` and `write`, or corrupt): if its mtime is older than 60 s, recover; otherwise exit 5 ("journal is very new, retry shortly").

Recovery first claims the journal with `fs.renameSync('journal.json', 'journal.recovering.json')`. `ENOENT` means someone else claimed it, exit 5. If `journal.recovering.json` already exists (a recovery was interrupted), it is used as the journal. `preview` and `doctor` only read the journal and report, with the same four-way decision phrased as information.

### Recovery algorithm (`recover.js`)

Input: the claimed journal, or none (unreadable). Output: the project restored to the pre-apply state, or the apply confirmed as committed.

1. If the journal is unreadable or has `state: "staging"` with no ops: delete every file in the scan scope matching `^.+\.cloudnaut-tmp-[0-9a-f]{8}$`, remove `.cloudnaut/backup/` if it exists, remove the journal. (No temp file can exist without an op recorded first, so this is a safety net for the unreadable case.) Done.
2. If `state === "committed"`: delete temp files named by the ops (if any remain), `backup/<id>/`, and the journal. Done ("committed").
3. Otherwise (`staging` or `applying`) roll back each op in reverse order:
   - `create`: if the file at `realPath` has `afterHash`, delete it; if it differs, leave it and warn.
   - `replace`: if the current hash equals `afterHash` and a backup exists, restore the backup via temp file and rename; if it equals `beforeHash`, nothing to do; if neither, leave it and warn.
   - `delete`: if the file is absent and a backup exists, restore it; if present, nothing to do.
   - Delete the op's `tmp` file if present.
4. Delete every remaining file in the scan scope matching the temp pattern for this journal's `id` (the id is in the journal). Remove directories in `createdDirs` innermost first, only when empty, except `.cloudnaut/`.
5. Delete `backup/<id>/`, then the journal.
6. Print each warning and continue. The next plan classifies leftover content normally (collision or local edit); nothing is lost.

Recovery is idempotent: each step checks hashes and existence, and the journal is the last thing deleted. A crash during recovery leaves `journal.recovering.json`, which the next run picks up.

### Fault injection for tests

`apply.js` calls `hooks.checkpoint(name, index)` at defined points. `checkpoint` is a no-op unless the exported test seam `setCheckpointHandler(fn)` is set; tests set a handler that throws. Checkpoints: `after-journal-created`, `during-stage:<i>`, `after-stage`, `after-rename:<i>`, `before-lock`, `after-lock`, `after-committed`, `before-journal-delete`. To simulate a hard process kill (no `catch`/rollback), the handler can throw a `CrashSignal`, which `apply.js` does not catch except to re-throw. Tests run both modes at every checkpoint, then call `apply` again, and assert the final tree equals a clean apply. A dedicated case covers a restore-only apply (a deleted owned file is restored; the lock bytes do not change) crashing between renames.

## Symlink and path policy (`paths.js`)

- `projectReal = fs.realpathSync(project)`. Refuse if it is not a directory, equals `fs.realpathSync(os.homedir())`, or is equal to or inside `<home>/.kiro`.
- Each target is a posix-relative path validated against the allowlist (R13.9) and rejected if it is absolute, contains `..`, a backslash, a NUL, or a drive letter.
- `resolveWriteTarget(rel)`: join to `projectReal` using `path.join`. Walk from the project root through each existing component with `fs.lstatSync`. For every symlink encountered, compute `fs.realpathSync` of that component. If the real path is not inside `projectReal`, fail with `ESCAPE` (exit 3). If the final target exists and is a symlink inside the project, `realPath` is its resolved real path (so the symlink is preserved, content goes to the resolved file). If a non-existent suffix remains, `realPath = realpath(deepest existing ancestor) + remaining components`.
- Containment: `path.relative(projectReal, candidate)` must not start with `..` and must not be absolute (this is correct for Windows drive letters). On `win32` and `darwin` the comparison is done on case-folded paths. Windows junctions are treated as symlinks (`realpathSync` resolves them). A broken symlink at a target is `TYPE_MISMATCH`.
- `paths.guard` runs for every target during planning (R18.1), for the `.cloudnaut/` journal, backup, incoming, and temp paths, and again in `doctor`.
- Unit tests call `isInside(root, candidate, platform)` with synthetic Windows-style and POSIX paths so the logic is tested on all runners even where symlink creation is not possible.

## Hashing

`hash.js`:

- `normalizeText(s)`: replace `\r\n` with `\n`. A leading BOM is preserved (it is content).
- `sha256Text(s)`: hex SHA-256 of UTF-8 bytes of the normalized text.
- `canonicalJson(v)`: stable serialization with sorted object keys, no whitespace. `sha256Json(v)` hashes it.
- `rawHash(buffer)`: SHA-256 of raw bytes, used only for journal before/after checks and `expectBeforeHash`.
- Packaged files are read as UTF-8 text. Binary files are not permitted in profiles (the generator rejects NUL bytes).

## Doctor

`doctor.js` returns `{ findings: [{category, code, message, target?}], summary }` with categories `OK`, `INFO`, `OPTIONAL_MISSING`, `BROKEN`. Checks, in order:

1. Project guard (exit 3 if refused) and lock read. No lock is BROKEN `NO_LOCK`; invalid is `LOCK_INVALID`.
2. `journal.json` or `journal.recovering.json` present: BROKEN `RECOVERY_PENDING` (the message includes the owner status: running apply, dead owner, other host). Stray files matching `^.+\.cloudnaut-tmp-[0-9a-f]{8}$` in the scan scope, or `.cloudnaut/backup/`: BROKEN `TEMP_LEFTOVER`.
3. Version: lock newer than tool is BROKEN `LOCK_NEWER`; tool newer than lock is INFO `UPGRADE_AVAILABLE` ("run preview").
4. For each item in the lock (excluding `preexisting`): file exists and hash compare gives OK, INFO `LOCALLY_MODIFIED`, or BROKEN `MISSING`. JSON entries: file parses (else BROKEN `UNPARSEABLE`), entry present (else BROKEN `ENTRY_MISSING`), `autoApprove === "*"` on any server key we own is BROKEN `BLANKET_AUTOAPPROVE`; local differing entry is INFO.
5. Extensions: `extensions.json` scans successfully and the ID is present, otherwise BROKEN.
6. Hook: if the lock has the hook item, parse it and require `version === "v1"`, exactly one hook, `trigger === "PostTaskExec"`, `action.type === "command"`, `action.command === "node .cloudnaut/run-verify.cjs"`, and no `matcher`; `.cloudnaut/run-verify.cjs` must exist and `.cloudnaut/verify-command.json` must parse to an object with a non-empty string `command`. Otherwise BROKEN `HOOK_INVALID`. `node` missing from PATH is OPTIONAL_MISSING `NODE_NOT_ON_PATH` (Kiro's PATH may differ; informational). Any file in `.kiro/hooks/` named `cloudnaut-*` that is not in the lock is INFO.
7. Unresolved incoming copies in the lock: INFO `UNRESOLVED_INCOMING`, with the path.
8. Symlink guard over all owned paths: BROKEN `ESCAPE`.
9. Optional prerequisites: `git` on PATH (OPTIONAL_MISSING `GIT_MISSING`, found by scanning `PATH`, not by running it); if the lock has CodeGraph: `codegraph` on PATH (scan only), then, unless `--no-exec`, the single `codegraph version` probe described in D13 and R8.6 (fixed argv, 5 s timeout, telemetry and update-check env vars; version parse rule: first `\d+\.\d+\.\d+` in stdout, else `CODEGRAPH_VERSION_UNKNOWN`; with `--no-exec`, `CODEGRAPH_VERSION_SKIPPED`), version equal to the manifest pin (else OPTIONAL_MISSING `CODEGRAPH_VERSION_MISMATCH`), and `.codegraph/` directory present, each with the exact command that fixes it (`npm install -g @colbymchenry/codegraph@1.6.4`, `codegraph init`, and so on). A spawn failure or timeout is OPTIONAL_MISSING, never BROKEN.
10. Exit 4 iff any BROKEN. The output prints sections in the order BROKEN, OPTIONAL MISSING, INFO, OK, so broken config is never buried.

## CLI surface

```
node bin/dev-setup.js preview --project <path> --profile <core|aws|connect> [--with-codegraph] [--with-ponytail] [--verify-command <cmd>] [--json]
node bin/dev-setup.js apply   --project <path> --profile <name>              [same options]
node bin/dev-setup.js doctor  --project <path> [--json] [--no-exec]
node bin/dev-setup.js --help | --version
```

Validation rules for inputs:

| Input | Required | Type and limits | On failure |
| --- | --- | --- | --- |
| `--project` | yes | existing directory; resolved with `fs.realpathSync` | exit 1 (missing/not a directory), exit 3 (home or `~/.kiro`) |
| `--profile` | preview/apply: yes unless a lock exists | enum `core`, `aws`, `connect` | exit 1 listing valid values |
| `--with-codegraph`, `--with-ponytail`, `--json` | no | boolean | unknown flag exits 1 |
| `--no-exec` | no, `doctor` only | boolean | on `preview`/`apply` exits 1 |
| `--verify-command` | no | string, trimmed, 1 to 1000 chars, no `\r`, `\n`, `\0` | exit 1; nothing is written |
| Positional command | yes | `preview`, `apply`, `doctor` | exit 1 |
| Lock file | n/a | validated as above | exit 6 |
| `mcp.json`, `extensions.json` | n/a | parse and shape as above | collision, exit 2 |

`parseArgs` is configured `strict: true` so unknown flags fail. Errors are `SetupError` instances; `cli.js` prints `error[<CODE>]: <message>\n  fix: <hint>` to stderr, prints the stack only if `DEBUG=cloudnaut`, and returns the mapped exit code. An uncaught exception maps to exit 6 and prints a one-line report with `DEBUG` hint. Nothing is written to log files.

Verify command handling: the CLI treats the command as an opaque string and never puts it in the hook JSON. It is written once, JSON-encoded, to `.cloudnaut/verify-command.json` (and the lock), and `run-verify.cjs` executes it with `spawnSync(command, { shell: true, cwd, encoding: "utf8", timeout: 590000, maxBuffer: 64 MiB })`. Forwarded output is bounded: the runner builds the combined stdout-then-stderr text and, if it exceeds 200 lines or 20 KB (whichever is smaller after truncation to the tail), forwards only the tail preceded by a line `... N lines truncated`. An `ENOBUFS` error (child output above `maxBuffer`) is reported as a failure with the line `verify command output exceeded 64 MiB`, the tail of what was captured, and a non-zero exit; docs state this limit. `cwd` is `path.resolve(__dirname, "..")`, the project root, independent of the process cwd. On non-zero exit, spawn error, or timeout the runner writes the child's stdout, then stderr, then a final line `verify command failed (exit N): <command>` (or the spawn/timeout reason) to its own stderr and exits non-zero; on success it prints nothing. Docs show how to pass the command so the user's shell delivers it intact:

- POSIX: `--verify-command 'npm test'`
- PowerShell: `--verify-command "npm test"` (use single quotes inside for inner quotes)
- cmd.exe: `--verify-command "npm test"`

Docs recommend the project's existing script name (`npm test`, `make verify`, `./gradlew check`) over inline pipelines. On Windows `shell: true` selects `cmd.exe` (Node documented behavior), so the command must be valid there; the runner makes this a property the developer can test by hand with `node .cloudnaut/run-verify.cjs`. The CLI emits non-blocking plan warnings: (1) when the command contains `|`, `>`, `<`, backtick, `$(`, or `%`, that shell behavior differs by platform; (2) when the command matches the secret patterns in R7.4, that it will be committed to Git. Doctor and docs say the same.

## Error handling (per operation)

| Operation | Failure | Recoverable? | Caller receives | Logged? |
| --- | --- | --- | --- | --- |
| Arg parsing | unknown flag, bad value | yes, user fix | exit 1, message with valid values | stderr |
| Project resolution | not a directory | yes | exit 1 | stderr |
| Project resolution | home or `~/.kiro` | no (user must choose another path) | exit 3 | stderr |
| Manifest load | missing file or hash mismatch | fatal for this checkout | exit 6, "re-checkout the tag" | stderr |
| Lock read | invalid JSON or schema | fatal until fixed by hand or Git restore | exit 6 (apply, preview), BROKEN finding (doctor) | stderr |
| Reading a target | `EACCES`, `EISDIR` | user fix | `TYPE_MISMATCH` or fatal with path, exit 2 or 6 | stderr |
| Symlink guard | escape | no | exit 3, nothing written | stderr |
| Planning | any collision | yes, user edits project | all collisions listed, exit 2 | stdout (list), stderr (summary) |
| Preflight re-check | target changed | yes, re-run | exit 2 | stderr |
| Journal found at start | owner alive, other host, or journal very new | yes (wait, or remove by hand after checking) | exit 5, nothing touched | stderr |
| Journal found at start | owner dead, or unreadable and older than 60 s | yes | automatic recovery, then apply continues | stderr (recovery summary) |
| Journal creation | `EEXIST` (lost the race) | yes | exit 5 | stderr |
| Recovery claim | `ENOENT` on rename (another recoverer) | yes | exit 5 | stderr |
| After `committed` | clean-up exception | yes (next run cleans up) | exit 6, no rollback | stderr |
| Staging | `ENOSPC`, `EACCES` | rollback runs, then user fixes | exit 6 and rollback report | stderr |
| Commit rename | `EPERM`/`EBUSY` on Windows | retried 5 times, then rollback | exit 6 | stderr |
| Rollback | cannot restore an op | journal and backups kept | exit 5, instructions | stderr |
| Recovery | content differs from journal expectations | file left alone, warning | continues, warnings printed | stderr |
| Doctor tool probes | spawn failure, timeout, or unparseable version | n/a | OPTIONAL_MISSING finding | stdout |
| Verify runner (in Kiro, not the CLI) | command fails, times out, or cannot spawn | n/a | non-zero exit with stdout and stderr on stderr | Kiro surfaces stderr to the agent |

Logging: v0.1 has no log files and no telemetry. Messages go to stdout (results) and stderr (errors and warnings). `DEBUG=cloudnaut` adds stack traces and the journal path.

## Invariant ownership

| Invariant | Owning layer | Why there |
| --- | --- | --- |
| Nothing is written outside the real project root | `paths.js`, called by `plan.js` for every target and by `apply.js` for every temp/backup/journal path | Single choke point; `apply.js` never builds a path itself |
| Only allowlisted target paths | `manifest.js` generator (build time) and `plan.js` (run time) | A bad manifest is caught at generation, and a tampered one at run time |
| Preview writes nothing | `cli.js` dispatch plus `buildPlan` having no write imports | `plan.js` does not import `fs` write functions; a test greps for them |
| Preview and apply use the same plan | `cli.js` calls `buildPlan` once, `apply` takes the plan object | No second code path to drift |
| No writes on collision | `plan.js` produces collisions, `apply.js` refuses non-empty `collisions` before step 3 | Defense in depth, tested at both layers |
| Idempotency | `plan.js` (`unchanged` and no lock write when bytes equal) | Decided from content, not from "already ran" flags |
| Atomicity and recovery | `apply.js` and `recover.js` only | Journal format is private to those two modules; commit state is the explicit `state: "committed"` marker, never inferred from file contents |
| One apply at a time | journal exclusive create plus owner record, liveness check, atomic claim by rename | Prevents a second process from rolling back a live apply |
| Verify failures reach the agent | `run-verify.cjs` (one module, no dependencies) | The only code on the failure path; tested through `child_process` |
| Hook only with explicit command | `manifest.js` desired-state builder (the `verifyHook` items, including `run-verify.cjs` and `verify-command.json`, exist only if `options.verifyCommand`) | Derived at the source of the item list |
| No blanket `autoApprove` | content lint (build) and `doctor` (run) | The CLI never writes it; both layers detect a hand-added one |
| No network or AWS access | no `net`/`http`/`https`/`dns` imports and no `.aws`/`AWS_`/home-path use outside `paths.js` (source-scan test), plus a run under `tests/helpers/block-network.mjs` | Structural, with a behavioral backstop; file access cannot be observed directly |

## Documentation design

- `README.md`: what it is, requirements (Node >= 22, Git), quick start (three commands), profile table, option table, exit codes, safety guarantees, links.
- `docs/releasing.md`: select release (`git fetch --tags && git checkout vX.Y.Z` in the Cloudnaut checkout), `preview --project <app> --profile <p>`, in the project `git switch -c chore/cloudnaut-dev-setup-X.Y.Z`, `apply`, `git status`, review the diff and `.cloudnaut/incoming/`, commit, open a PR, and rollback with `git revert <commit>`. Also a maintainer section: update `CHANGELOG.md`, run `npm test && npm run check`, then tag `vX.Y.Z` (the maintainer's step).
- `docs/onboarding.md`: from clone through `doctor`, Kiro MCP setting, first skills and steering check, AWS Toolkit install and sign-in check using the developer's own profile (`aws sts get-caller-identity --profile <your-profile>` shown as the developer's own check, not run by the CLI).
- `docs/smoke-test.md`: table with step, expected result, label (`RAN LOCALLY` or `NEEDS LIVE IDE`), and the last result and date. Live-IDE rows include: deliberately failing stdout-only verify command reaches the agent (R7.8), and the Windows `codegraph.cmd` launch (R8.8).
- `docs/hook.md`: install with `--verify-command`, what the runner does, quoting for POSIX/PowerShell/cmd.exe, the secrets warning, how to test by hand (`node .cloudnaut/run-verify.cjs`), the stderr-only surfacing rule, and the fact that `PostTaskExec` cannot block.
- `docs/codegraph.md`: pinned install, init, verify, `.codegraph/` ignore, telemetry layers, the `codegraph version` probe used by `doctor` (and `--no-exec`), and the unverified Windows `.cmd` launch risk.
- `docs/maintainers.md`: public-content checklist, review of CodeGraph and Ponytail pins, license decision.

## Mapping to the requested implementation order

1. Repository structure, manifest, baseline content: layout, `package.json`, `.gitattributes`, `profiles/*` content, manifest generator, `scripts/check-content.js`, layout and content tests, README skeleton, CI file.
2. Preview, apply, doctor, upgrade, tests: `src/*`, installer tests, fixture.
3. AWS and Connect integrations, optional tools, onboarding, smoke test: MCP, extensions JSONC, hook, CodeGraph, Ponytail vendoring, Power and sync script, docs, `smoke-local.js`, final report.

(Tasks 1 and 3 touch the manifest, so 1 defines manifest fields for all features up front, and 2 consumes them.)
